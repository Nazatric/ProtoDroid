## 1. PrototypeRecomp — semantic reference, not a performance patch source

### Code traced

- `runtime/gdfx_volume.cpp::GdfxVolume::Read` performs a binary search over sorted disk regions and positioned `pread` calls while holding `io_mutex_`. This is real region lookup and host I/O, not a claim inferred from the README.
- `runtime/imports_fs.cpp::NtReadFile`, `NtWriteFile`, and `NtReadFileScatter` complete the host read/write and IOSB before `QueueIoCompletionApc`; only then do non-synchronous handles return `X_STATUS_PENDING` and signal completion. The guest-visible asynchronous APC/event ABI is implemented, but there is no host asynchronous I/O worker hidden behind it.
- `runtime/gpu_command_processor.cpp::XenosCPMain` has a real command-processor thread, ring/doorbell handling, packet counters, wait handling, and interrupt dispatch. Draw and shader opcodes remain a frontier in the audited implementation; this is not an Android Vulkan renderer whose batching can be benchmarked as ProtoDroid evidence.
- `runtime/state.cpp` and `runtime/imports_vd.cpp` implement guest threads/APCs and Xbox display/ring semantics. PowerPC/Xenon behavior must not be conflated with ProtoDroid's existing x86 static recompilation.

### Evidence and applicability

The README's Android/Vulkan wording is a target, while the pinned tree explicitly remains WIP. No controlled Android FPS result was found. Fresh production-code tests at the same pin add the following evidence:

- The repository's own `scripts/test_gdfx_volume.cpp`, compiled with the real `runtime/gdfx_volume.cpp`, passes on a deterministic synthetic tree: six files/two directories, recursive BST traversal, four nonzero host-file byte-identity windows, EOF clamping, and 64 KiB structural reads. ASan/UBSan also passes. The fixture is synthetic, not original game content.
- A separate unchanged-production `GdfxVolume::Read` probe verified all 8,388,745 payload bytes through 617 irregular reads. Eight threads completed 1,024 observed 16 KiB `pread` calls (16 MiB) with zero mismatches and `max_active_pread=1`; the production mutex therefore prevented overlap. A clearly labelled 200 µs synthetic-delay case took 17.845 ms with one thread versus 18.587 ms with four for the same 64 calls (ratio 1.042), consistent with serialization rather than parallel host I/O. These are x86_64 host observations, not phone loading or frame times.
- Removing a synthetic backing file after `Build` but before lazy open produced a full-length 4,096-byte read of zeros, matching the source's explicit zero-fill/device-semantics branch. This is recorded behavior, not hidden corruption or evidence that missing game data is safe.
- The custom probe also passes ASan/UBSan and TSan. Raw logs are `audit/tests/prototype-recomp/run-{existing-test,io-probe}*.log` in the persistent evidence store.

GDFX region search and its global read mutex are not reasons to replace ProtoDroid's existing RCF index or per-fd `pread` path. ProtoDroid's `kernel32.cpp` has no equivalent global GDFX lock and already has opt-in detailed read/write timing, slow-event attribution, and error counters. Synchronous host reads followed by guest `PENDING` semantics are not an asynchronous-I/O optimization. **Disposition: useful for semantic comparison; no 0.16 production technique adopted.**

## 2. Black-mobiu — real implementations in a different D3D8 renderer

### Code traced

- `native/vk_shader.cpp`: versioned SPIR-V filenames, cache load validation, temporary-file-plus-rename stores, and a mutex around glslang translation. On a miss, HLSL parsing/linking/SPIR-V emission is synchronous; this is not an asynchronous shader compiler.
- `native/vulkan.cpp`: Vulkan 1.1–1.3 selection, extension checks, `VkPhysicalDeviceFeatures2` feature queries, format-feature checks, dynamic-rendering/timeline fallbacks, and real `vkCreateGraphicsPipelines` calls. `SavePipelineCache` serializes the driver cache; `Present` calls it every 600 presents. Idle cache work is separately bounded around 600 idle frames.
- `src/d3d/render_thread.cpp`: 64-command batches, recycled `Batch` objects, a worker queue, condition-variable waits, 64-byte state-delta pieces with NEON comparisons, resource-use tracking, and conditional readback only for surfaces written by the GPU.

### Evidence and applicability

These mechanisms exist in code, but this repository supplies no matched ProtoDroid/DXVK measurement. A fresh component probe compiled the actual `vk_shader.cpp` with only glslang replaced by deterministic stubs:

- HLSL `1.#INF` adaptation, vertex-attribute location insertion, versioned cache naming, round trips, empty/non-word-size rejection, and warm hits behaved as written.
- The loader accepted a four-byte opaque cache file without invoking the stub compiler. `VulkanBackend::Module` subsequently calls `vkCreateShaderModule`, so real driver/module rejection remains a separate gate; no claim of successful rendering from invalid data is made.
- Six orchestrated direct cold calls for one key all missed before any store and performed six serialized compilations (`max_active_compilations=1`); the following warm call did not compile. Stress produced 64 unique files and varied duplicate-compile totals across runs (77 ordinary final, 78 ASan/UBSan, 79 TSan). A second call with the same opaque key again loaded the entry without recompilation, so the accepted entry does not self-heal through this path. This establishes component behavior only. The actual caller hashes source+entry+stage and memoizes modules, while `render_thread.cpp` executes inner-backend draw calls on its render worker; the direct probe does **not** prove duplicate compilation in the real game workload.
- Corrected final probes pass normally and under ASan/UBSan/TSan. Initial stub mismatches, a wrong harness expectation, and a harness `std::vector<bool>` bit-packing race are preserved with their corrected reruns. Stubbed glslang means no real HLSL/SPIR-V, Vulkan, rendering-correctness, loading-time, or FPS claim.

Its renderer and resource model are not drop-in replacements for Android-patched DXVK 2.5.3. DXVK's state cache stores pipeline state/keys with SHA-1 integrity, not Black-mobiu's per-source SPIR-V file format. Capability/fallback structure is a useful correctness reference; batching, state delta, and cache cadence remain candidates only if ProtoDroid profiles show equivalent costs. **Disposition: selectively useful ideas, no wholesale renderer, synchronous shader path, or cache-format import.**

## 3. GoW III Daedalus fork — substantial code, mixed PC and Android evidence

### Code traced

Under `gpu/shadps4/video_core/renderer_vulkan/`:

- `vk_async_compiler.h`: bounded normal/urgent queues, worker initialization, queue-wait counters, stop/drain behavior, one-job-per-entry futures, and recyclable compiler pools. Queue-full submission fails so the caller can use its fallback.
- `vk_pipeline_cache.cpp`, `vk_pipeline_serialization.cpp`, and `driver_cache_file.h`: runtime/warm-up pipeline creation, per-worker caches, merging/snapshotting, optional pipeline-binary persistence, driver identity/header/checksum validation, and atomic cache-file replacement.
- `vk_draw_prep.cpp` and `vk_draw_prep.h`: speculative command/register/resource preparation with GPU-thread validation and fallback. This is correctness-sensitive work, not unconditionally trusted stale guest data.
- `vk_scheduler.cpp`, `vk_draw_pipe.h`, and related recorder paths: segmented recording, worker handoff, ordered execution, and drains for non-pipelineable operations.
- `vk_staging_buffer_pool.cpp`: block reuse and retention. Defaults include eight 16 MiB prewarmed blocks (128 MiB) and a 512 MiB retention setting.
- `vk_shader_hle.cpp`: game-specific MultiCopy/HLE work, not a generic D3D9 optimization.

### Evidence context

- `docs/parallel_gpu.md` contains real PC test-scene A/B numbers, including roughly +18–32% for stages of the draw pipeline, +11% for the constant ring, +9% for render-state memoization, and +5.6% for texture-set memoization. The document also records neutral and slower experiments. These measurements use desktop/high-thread/RX 7800 XT contexts and often FSR/test-specific settings; they are not Android or ProtoDroid gains.
- `docs/ANDROID_PERFORMANCE_DELTA_025.md` explicitly says its investigation is not a measured Redmagic FPS gain. It disables Android speculative draw-preparation workers by default, retains two Android compiler workers, and calls the two-queued-frame policy a latency/throughput tradeoff requiring controlled validation.
- `docs/ANDROID_BACHATA_OPTIMIZATIONS.md` describes ARM64 SRT and driver-cache tests but likewise says code tests do not establish an FPS gain. `docs/ANDROID3_PORT.md` leaves hardware validation to the user.

### Applicability

The bounded-queue/backpressure, validation, and low-contention principles are useful. ProtoDroid already caps Mali DXVK compiler workers at two and serializes affected Mali driver pipeline calls, so importing more workers would not reproduce the GoW III architecture or prove more parallel driver compilation. Large staging prewarm/retention is inappropriate without a memory/profile justification. **Disposition: candidate principles only; no FEX, PS4 renderer, HLE, PGO profile, upscaler, or large-memory default import.**

## 5. Bloodborne-Android — controlled Adreno evidence with important negative results

### Code traced

### Evidence context

- AOT versus the earlier FEX runtime at one save was 29.7/29.4 FPS; a later 169-sample strict-AOT session averaged 29.2 game FPS while 60 shown frames used frame generation. Generated frames are excluded from any technique conclusion here.
- Copy mode versus unified-memory work at one controlled spot was 5382→4944 MB PSS at 24 FPS: a memory saving, not an automatic FPS increase. Later blocking-wait/pinning runs used different settings and are not silently merged into that comparison.
- The session document records a Thor hard reset when shared dma-buf memory was sparse-bound through KGSL, a race fixed during 32 MiB-granule testing, and thermal collapse on another device. The README says Mali is unsupported/testing-only at this pin.

### Applicability

ProtoDroid already has the same open-addressed multiplicative-hash dispatch structure in `src/native/runtime.cpp` and `src/recomp/bridge_x86.cpp`; replacing it with the Bloodborne table is not a new optimization. Strict-AOT results caution against assuming a CPU architecture rewrite raises GPU-bound FPS. Unified-memory code is PS4/Adreno-specific and carries serious coherence/driver risk; the focused unmodified UBSan run also stops on its initial zero-length null-`memmove` VMA edge case, while only a test-only guarded copy completes. It is not a DXVK patch. This rejection does **not** apply to ProtoDroid's existing `dxvk-unified-memory.patch`: that is a backport of upstream DXVK `866228a37dd644ae89a66db369f80f10d9462ae3` fixing compatible memory-type candidate masks on Qualcomm unified-memory drivers, not a shared-guest-memory optimization. Short-spin-then-block is a possible later scheduling experiment only where ProtoDroid profiles show spinning/wake latency. **Disposition: useful measurement lessons and negative evidence; no AOT/FEX/UMA/affinity/frame-generation import; retain the unrelated DXVK compatibility backport.**

## Baseline equivalence check — DXVK 2.5.3 source

This is a dependency check, not a sixth mandatory repository or a replacement proposal. The exact tag used by `android/build-deps.sh` was cloned separately at `v2.5.3`, commit `c707d9026f33b6ab89639f154b6ac5f6326fa037`; its `LICENSE` is zlib/libpng, SHA-256 `a5cb1a6ded7d2d7e92d550ba28edd21be2d1d4044662b399887351023e30ce64`. - `src/dxvk/dxvk_pipemanager.cpp::DxvkPipelineWorkers`: workers start lazily, use lowest thread priority, and consume normal/high/low-priority queues. ProtoDroid's Android patch caps this existing worker pool at two on Mali; it does not need a second async-compiler architecture imported from GoW III/ISS.
- `src/dxvk/dxvk_state_cache.cpp::registerShader`, `compilePipelines`, `workerFunc`, and `writerFunc`: resolved cache entries dispatch background pipeline compilation, while a separate writer persists new entries. `DxvkStateCacheEntry` contains pipeline state/shader keys and a SHA-1 integrity hash, not a Black-mobiu-style SPIR-V payload; the upstream write path flushes each entry. Thus warm-cache background compilation and durable pipeline-state I/O are baseline concepts, not new external techniques.
- `src/d3d9/d3d9_device.h`, `d3d9_options.cpp`, and `d3d9_swapchain.cpp`: D3D9 has a default frame-latency value of 3, a `d3d9.maxFrameLatency` option, and a real wait in `SyncFrameLatency`; the effective value is also bounded by back-buffer count. A future queue-depth A/B can use the existing configuration surface, with explicit latency/pacing checks, rather than a renderer rewrite.
- `src/d3d9/d3d9_device.cpp::SetRenderState` checks whether a value changed; `PrepareDraw` consumes dirty texture/sampler/state masks. `EmitCs` fills 16 KiB command chunks, `DxvkCsChunkPool` recycles chunks, and `DxvkCsThread` executes queued chunks with condition-variable synchronization. Black-mobiu's broad batching/recycling/state-delta concepts therefore already have DXVK equivalents, although their exact costs still require local profiling.
- `src/dxvk/dxvk_staging.cpp` and D3D9 staging calls: uploads suballocate from a current 4 MiB linear staging buffer, oversized requests get separate buffers, and `WaitStagingBuffer` uses a 64 MiB in-flight threshold on 64-bit hosts. Reuse and memory throttling are not new ideas; the external difference is aggressive multi-block prewarm/retention, which must not be compared as though it were the same memory metric.
- `src/d3d9/d3d9_device.cpp::WaitForResource` and `src/dxvk/dxvk_device.cpp::waitForResource`: resource-access waits flush/synchronize as required and already accumulate `GpuSyncCount`/`GpuSyncTicks`.
