## Source-led hypotheses

### H1 — normal Play pays for disabled Present diagnostics

`src/dxvk/dxvk_presenter.cpp` in `dxvk-android.patch` calls `nowUs()` around queue pre-acquire and updates `g_preFenceUs`/`g_preAcqUs` on every presented frame regardless of `DXVK_PRESENT_STATS`. The application-side acquire fallback similarly clocks and updates three counters. In contrast, `D3D9SwapChainEx::PresentImage` gates its own clocks/counters on a lazy `statsOn` read after the host sets the environment.

Candidate: propagate that one-time option state through a relaxed atomic flag and retain a non-instrumented Vulkan path when disabled. The wait, acquire, queue-present, frame-index, semaphore, fence, and result operations must remain identical; enabled mode must retain the original measurements and 300-frame report. Benchmark only the exact diagnostic scaffolding on host/native ARM64; this is not an Android FPS measurement.

**Rejected as immaterial; production candidate reverted.** The exact full-patch source passed function extraction, lazy-publication identity, success/suboptimal/error paths, call order, semaphore/fence state, feature-chain, enabled/disabled counter, cross-thread publication, ASan+UBSan, and TSan tests. The fixture baseline compilation unit was reconstructed with only `dxvk-android.patch`; a nine-check follow-up proves its globals/acquire/Present/wait parts identical to the restored all-16-patch Presenter (SHA-256 `3051cf785c3f29a5f9d3dcc4e31d33466e345f1f8ec7a09c3745eece5bac9a38`) and the candidate an exact target-part transform. Absent DXVK `present:` submit/acquire/latency decomposition, do not blame the swapchain for long engine/render intervals or change FIFO, image count, frame latency, or lock ownership.

### H5 — frame signaling and limiter semantics

The historical Mali device reports `presentId=0` and `presentWait=0`, so its presenter uses the direct limiter/signal path; `dxvk-frame` optimization would not affect that run. Direct signaling still applies the FPS limiter before releasing the frame-latency fence. Zero-interval mode resets schedule state, negative vsync intervals use the refresh/max-latency heuristic, and sleep occurs outside the limiter mutex. `frameId` starts at `MaxFrameLatency`, repeated presents use ID zero, destruction waits with acquire semantics, and present-wait requires present-ID. Removing or bypassing these operations would alter pacing/reconfiguration/lifetime behavior, not merely reduce overhead.

**Disposition: no runtime candidate.** `tools/test_dxvk_frame_pacing.py` passes **25 checks**. Direct-limiter removal, destruction-wait removal, sleep-under-lock, and zero-initial-frame-ID mutations are all detected; one control-setup indentation failure is preserved before the passing run (`frame-pacing-controls.json`). No limiter, signal, present-wait, or queue-depth change is justified by the historical low Present-wall data. This is structural correctness evidence, not measured input latency or frame pacing.
